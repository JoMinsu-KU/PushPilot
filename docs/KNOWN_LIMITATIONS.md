# Keep the demonstration claim precise.

**As of November 2, 2026.** The initial public baseline `7aa7753` is followed by the scoped Native-recovery implementation/deployment `bcac769`. PushPilot connects a tablet plan to an explicitly configured current-site robot trial. This page records the boundaries of that implementation; historical tests retain the narrower claims in their original records.

| Area | Implemented or evidenced | Remaining limit |
| --- | --- | --- |
| Product scope | Default simulation and a separate private `site_trial` Robot path with actual receipts, MUSE reviews and empty return. | A public checkout alone has no active robot recipe, private runtime, hardware profile or camera registration. Publication is not activation. |
| B/C/D delivery | Historical actual arrivals at Office, Villa and Hanok are preserved; all three destinations are represented in the configured recipe path. | Trials included operator decisions, failed fragments and recoveries. They do not establish unattended repeatability of every later composed recipe or installation. |
| C endpoint | C26 is the selected Villa delivery endpoint, with destination/zone review and subsequent empty START return. | C25 is not selected merely because it may look closer. C27/C28 and final straightening are omitted in this release. |
| Alignment | Generic policy and measurement interfaces support independently qualified correction envelopes. | Active delivery-only behavior defers numeric straightening and parallel parking. No millimetre/yaw qualification is inferred from a qualitative MUSE PASS. |
| Coordinate authority | Taught BASE geometry, current-source profiles and independent Native endpoint checks. | The rejected board-to-BASE fit remains rejected. Camera display registration, robot TCP travel and car travel are different quantities. No general whole-map contact-accurate transform is established. |
| Contact mechanics | Coordinate approach/contact/release/withdrawal with bounded stages; selected experimental turn evidence retained. | Rubber deformation, slip, force/contact state, full gripper/arm/hose swept clearance and physical car response are not guaranteed by geometry screening or software replay. |
| Perception | Original-frame reviews, fixed reference lineage, same-coordinate C4/C6 details, C14 clear reference and qualitative C progress. | Occlusion, white-body front/rear ambiguity and inconsistent judgments remain possible. Null stays unknown. Later review is not guaranteed to catch an earlier missed problem. |
| Signal | Two printed faces, black circular cover, two-frame MUSE review and one accepted stopped GREEN admission before exact recontact/continuation. | Manual mask swaps remain ambiguous when both colors are substantially exposed. This is a demonstration observation policy, not an independent physical traffic interlock. The requested physical 120-second wait needs exact deployed-configuration verification. |
| Camera/AR | Native preview and shared image/route transforms; fixed references can survive expected marker occlusion. | Decode/stale or confirmed-view-change guards can hide overlays. A locked display is not metric robot calibration or proof of a fresh car observation. |
| Idle connection | Separate listener and legal-idle Native read recovery; `native_wait` prevents stale admission and the durable ledger blocks unknown replay. [Details](HOST_NATIVE_RECOVERY.md) | Non-idle handshakes, wire/controller faults and request-expiry boundaries can still terminate a session. No automatic pendant reconnect or unknown-command replay. Source tests do not qualify a live idle soak or loaded route. |
| Recovery | Narrow completed-review continuation, C11 preparation and session-scoped START precision reference. | They do not resume arbitrary interrupted movement, repair controller faults or change the original common START. Reset is no-motion; empty return requires its own evidence. |
| Empty return | Separate reviewed return recipes and robot endpoint checks. | Car reset is separate. Historical D return candidates are not all physically exercised; a changed actual source requires a newly bound reviewed return. |
| Voice/tablet | Text goals and current workspace operate over the selected LAN setup. | Browser microphone capture requires a trusted secure context and its own verified capture/normalization path. LAN HTTP availability does not establish voice readiness. |
| Goal editing across modes | Robot UI disables goal editing during its active mission; simulation endpoints validate their own workspace state. | A server-side lock shared by the workspace/voice endpoints and separate physical service is not implemented. Direct API callers must not treat UI gating as cross-service enforcement. |
| Request coordination | Dedicated camera/physical display transports have bounded reads and sequential polling. | Shared Start/Stop pending state, symbolic-provider inference under the workspace lock, historical Stop replay side effects and general request deadlines remain [open findings](REVIEW_FOLLOW_UP.md#code-findings-remain-open). This documentation update does not repair them. |
| Public CI and accessibility | The recorded-review Pages workflow verifies its narrow static artifact. | Full application CI and the custom Select's active-candidate announcement are follow-ups, not completed changes. [Review scope](REVIEW_FOLLOW_UP.md) |
| Evidence | Source checks, offline tests, archived-image evaluations, point-in-time deployment inspection and historical physical logs are distinct. | None alone establishes a recognition accuracy benchmark, contact simulation, current equipment readiness or production qualification. |
