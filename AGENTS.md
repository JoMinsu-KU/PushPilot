# PushPilot application workspace instructions

- This directory is the independent application repository boundary for new PushPilot implementation. Keep it runnable and packageable without files outside this directory.
- Use English for source code, identifiers, comments, errors, logs, tests, frontend copy, accessibility text and development documentation. Explain work to the user in Korean unless requested otherwise.
- Preserve the existing parent project, POC sources, handoff archives and historical evidence. A new repository does not make inherited work newly authored. Record any future import with its source/version, rights and exact changes in `CONTRIBUTIONS.md` and `THIRD_PARTY_NOTICES.md`.
- Product direction is a dark navy/electric cyan tablet workspace, following Observe → Plan → Approve → Act → Verify. AR glasses are a clearly labelled future companion concept. Do not imply connected hardware, voice input or spatial AR registration when unavailable.
- Voice goal input is part of the planned initial demo: bounded push-to-talk audio goes through the backend Meta Voice adapter, then editable original-language text, MUSE interpretation and explicit tablet plan approval. Keep typed input available. Provider credentials remain backend-only; transcripts never grant motion authority. Streaming and TTS are later options. See `docs/VOICE_INPUT.md` and `docs/SERVICE_COMPOSITION.md`; voice capture and transcription are not yet implemented or verified.
- Accept new typed/spoken goals only during non-executing preparation, never during an active mission or signal/review wait. A replacement requires explicit completion/termination and reconciliation. Plan trusted target-device HTTPS for microphone capture, and validate/normalize bounded recordings to Meta's supported mono 16-bit PCM WAV format before dispatch.
- The confirmed mission starts at symbolic PIZZA and pushes a wheel-less car on the surface toward a selected destination. Do not pick up or carry the car. Pushing and contact turning require later physical qualification.
- At every configured intersection, stop before the stop line even if the signal is green. After verified stopping, RED means wait; unknown, stale or obscured observations also inhibit entry. Fresh GREEN plus accepted local and MUSE checks permits automatic entry. Complete the qualified admitted crossing before the next approach. In-flight red interruption is outside the current scenario.
- Operator-switched red/green paper signals need a local observation/inhibition path separate from slower model review. Never describe web HOLD or terminating a server as immediate robot stopping.
- Keep map-dependent production development on hold: final road geometry and installation are unknown. Do not collect robot coordinates, fit camera/BASE registration, finalize road routes, stop lines or signal ROIs, or extend the old v11 adapter. User-provided temporary prints may support labelled vision-input tests under docs/TEST_INPUTS.md; they do not establish production geometry or physical execution. Keep private map artwork outside Git and source packages.
- Each bounded action must eventually be followed by fresh-image MUSE review and deterministic local checks before continuation. Goal understanding, expected-versus-observed comparison, uncertainty and the resulting decision must be visible. The model does not emit robot scripts or authoritative coordinates.
- Preserve source labels independently for robot state, image, car pose, signal and model result. Current actions/signals are simulation and review verdicts are operator-injected demo data. Meta goal interpretation does not establish image review: capability flags for robot, camera, registered_ar, voice and image_review remain false. A real provider on recorded images is provider evidence, not physical-execution evidence. Never turn a failed actual-provider request into a silent demo fallback.
- Prioritize the map-independent mission supervisor, operator UI, provider adapter, immutable decision evidence and replay. Robot transport and physical execution are excluded from this simulation application. No robot command, service restart, profile replay or mailbox restoration is authorized by ordinary code work.
- Keep secrets, local environment files, raw operating profiles, robot mailboxes, private media and full handoff archives out of Git and release packages. Use `.env.example` and reviewed example configuration only. Do not ask for API keys in chat.
- The first implemented slice uses a React/TypeScript/Vite frontend and Python 3.12+ FastAPI/Uvicorn backend with SQLite, revisioned commands, abstract simulation, and a strict-schema Meta goal adapter. Keep dependencies pinned in requirements.lock and frontend/package-lock.json. Node 24 is local build tooling; GX10 serves compiled frontend/dist with Python and one worker. Run `python tools/dev.py check`, `python tools/dev.py test`, and the frontend build before delivery. Preserve meaningful mission/API failure tests and visual layout checks.
- GX10 deployment must use a separate release directory and shared state. Read-only inspection on 2026-10-27 found Ubuntu 24.04.4 aarch64 and Python 3.12.3, with no Node/npm on the inspected PATH. The application is not installed or activated there; proposed paths remain unprovisioned. See `deploy/README.md`. Do not modify POC web, camera or receiver services to deploy this application.
- Do not publish a repository, choose a software license, submit to the competition or contact organizers without the user's corresponding authorization. Preserve accurate contribution dates and evidence; never backdate history.
